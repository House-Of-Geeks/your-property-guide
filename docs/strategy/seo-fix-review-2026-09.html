How to read each item

Every fix has the same five parts. Risk is graded on what it could break, not on effort.

PartWhat it answers
ChangeThe one thing being done, scoped so it ships as a single revertable commit or a single content edit.
Could breakThe unintended consequences found by reading the code and the data: what is working today that this touches.
GuardrailsThe checks, gates, staging and tests that have to exist before and during the change.
Ship whenThe observable condition that says the guardrails held.
RollbackHow it is undone, and how quickly.

Rules for every change

These exist so that no single fix can take down something that works. Several are missing from the repo today and are the first things to build.

  • R1Read the Next 16 docs in the repo before touching a route. AGENTS.md warns this version differs from training data. The relevant guides are in node_modules/next/dist/docs/01-app/02-guides/: caching-without-cache-components, incremental-static-regeneration, revalidatePath.
  • R2Baseline before, measure after. Before any item: save the Search Console page export for the affected template, a Bing page-stats pull, a Clarity 3-day pull and the current Bing 5xx count under docs/seo-baselines/YYYY-MM-DD/. Re-pull at 14 and 28 days. No baseline, no change.
  • R3One template change at a time, with a change log. Add docs/strategy/seo-change-log.md: date, item number, what changed, cohort. Search Console and Bing movements are only attributable if changes are spaced; leave 14 days between changes to the same template.
  • R4Stage by cohort, not by switch. There is no feature-flag system in the repo. For template changes, roll out by state (SA and TAS first: about 10% of suburbs, low traffic) using the slug suffix, watch for 14 days, then widen. Preview deployments on Vercel for everything before main.
  • R5URLs are permanent. No new URL for an intent that already has a page. Check the guides sitemap first: it already holds eight stamp-duty state guides, eight renters-rights guides, eight first-home-buyer guides, a FIRB guide, a fastest-growing-suburbs guide and two cheapest-suburbs guides. A new page that overlaps one of these gets a redirect plan or is not built.
  • R6Titles are tested. Add tests/seo/titles.test.ts: every title builder in src/lib/utils/seo.ts stays under 60 characters before the brand suffix, and no description contains a dollar figure when hasReliablePrice is false. Vitest already runs in CI-style via npm test.
  • R7Schema matches the page. FAQPage JSON-LD only carries questions that are rendered as visible text, which is how SuburbFAQ.tsx works today. After any template change, run five sample URLs through Google's Rich Results Test and the Schema Markup Validator.
  • R8Every number passes a gate with a test. src/lib/suburb-data-quality.ts already has hasReliablePrice, isPlausibleHousePrice, isPlausibleAnnualGrowth (±25%) and isPlausibleGrossYield, with tests. Any new figure rendered on a suburb page goes through one of these or a new sibling with its own test. Zero means "unknown, don't print"; keep that convention.
  • R9Deploy timing protects the database. Every deployment empties the on-demand ISR cache for about 37,000 pages; the July outage was an IndexNow ping sending a crawl wave at a fresh deploy. Do not deploy within two hours of the sync cron or an IndexNow submission, and warm the top 500 suburbs by impressions with a script after each deploy before anything is pinged.
  • R10Rollback is one action. Each code item is one commit on main, reverted with Vercel's instant rollback. Each content item keeps the previous copy in git. Nothing is combined into a multi-item release.
  • R11The lead funnel is watched. Any change to a page carrying an appraisal, selling-guide or expert CTA is followed for seven days in the leads-health cron count (newsletter sign-ups excluded, as it already does). A drop of more than 20% week on week reverts the change first and investigates second.
  • R12Published figures are sourced and dated. Any rate, threshold, grant, law or commission figure carries a source link and an "as at" date. Investment-flavoured text describes what the data shows and never recommends; the general-advice line that the finance guides already carry goes on every page that gets it.
  • R13API budgets are respected. Clarity export: 10 calls a day. Bing URL submission: 100 a day, 2,600 a month, changed URLs only. DataForSEO: about $0.003 per SERP, $12 left on the account. Scripts read keys from .env and log their usage; nothing is hard-coded.

Guardrails and crawl

01

Provenance and plausibility gate on suburb stats

Medium riskcode

Change. Render source, sample and period under every median; hold any median more than 25% off its region for review; keep dollar figures out of meta and opening copy when the source is a proxy; suppress population and region for suburbs missing from the 2021 ABS geography.

Could break
  • Morayfield's $1,095,000 passed the existing gates, which means its source is classed as reliable. A region-relative gate would hide the symptom while the feed keeps producing the figure (a sales-mix or acreage inclusion is the usual cause). The gate could suppress medians on thousands of legitimate outliers too: Toorak against its region, coastal towns against their shire.
  • Suppressing a median removes it from the snippet, the FAQ and the JSON-LD on every affected page at once. The suburb pages carry 71% of impressions.
  • The census-geography fallback is what gives Badagarang 48,267 residents; changing it touches every suburb that relies on the same fallback (about 30% per the pipeline notes).
Guardrails
  • Investigate Morayfield's feed first: pull the underlying sales rows for 4506 and compare the median with and without rural-residential lots. Fix the pipeline if that is the cause; the gate is the backstop, not the fix.
  • Build the gate in report mode before enforce mode: a script that lists every suburb it would hold, with its region median, the deviation and the source. Sample 30 by hand across states. Only then flip it to enforce.
  • Extend suburb-data-quality.ts rather than adding logic in components, with tests beside the existing ones in tests/lib/suburb-data-quality.test.ts. Use the same zero-means-unknown convention (R8).
  • Provenance text comes from the existing DataFreshnessNote component and statsSource field; do not invent a parallel source of truth.
Ship whenThe report-mode list is reviewed, the count of suppressed medians is known and accepted, and the Morayfield root cause is understood.
RollbackOne commit; the gate is a pure function, so reverting restores every figure at the next revalidation.

High riskcode

Change. In src/lib/utils/seo.ts, lead with suburb, state and postcode, then house prices, rent, schools and profile; open the description with the median, the 12-month change and the source month.

Could break

Guardrails

  • Keep the postcode in the title and keep the H1. Keep the description under 155 characters and free of dollar figures where hasReliablePrice is false (R6 test).
  • Item 4 lands first, and item 3 ships with this one, since the snippet comes from the opening copy.
  • Log the date (R3). Do not touch the title again for 90 days after the full rollout regardless of result.
Ship whenThe cohort's CTR is higher than the control at three weeks and its postcode impressions have not fallen more than the control's.
RollbackRevert the commit; the previous template is in git. Google takes weeks to re-read either way, which is why the cohort exists.

04

Take the database out of the crawl path

High riskcode
Rewritten by this review. The live cache headers show the suburb profile and its schools sub-page are served from ISR correctly (7-day revalidate, cache HIT). The rental-market sub-page (1,513 in the sitemap) and the school pages (9,670 in the sitemap) answer cache-control: private, no-store on every request: they are rendered from the database every time a crawler touches them. Neither route declares a revalidate. Add to that the runtime pool of one connection per instance with a two-retry backoff in src/lib/db.ts, and every deployment emptying the ISR cache, and the July 5xx wave is fully explained.

Change. Three steps, separately: (a) add the same ISR exports the profile page uses (revalidate = 604800, dynamicParams = true, empty generateStaticParams) to the rental-market and school routes; (b) prebuild the top 500 suburbs by impressions in generateStaticParams so they never hit a cold cache; (c) put a connection pooler in front of Postgres and return 503 with Retry-After from a circuit breaker when the pool is saturated.

Could break
  • Step (a) makes rental and school data up to seven days stale after a sync unless the sync revalidates those paths. Today the sync cron only pings IndexNow; the /api/revalidate route exists but nothing calls it for suburbs.
  • Step (b) lengthens the build: 500 pages with several parallel queries each against a build pool of 10 connections × 3 workers. A build that times out blocks every deploy.
  • Step (c) changes DATABASE_URL and the pool mode; Prisma 7 with the pg adapter and PgBouncer in transaction mode disallows some features (prepared statements, advisory locks). A 503 breaker that trips on user traffic turns a slow page into an error page for people, not just bots.
  • The docs warn this Next version differs; a wrong export silently makes a route dynamic again.
Guardrails
  • Do (a) first and alone. Verify on the preview deployment with two GET requests per route: the second must show x-vercel-cache: HIT and x-nextjs-prerender: 1. Add a test that asserts those routes export revalidate.
  • Wire the sync cron to POST the changed suburbs' paths to /api/revalidate (same key as IndexNow) before the IndexNow ping, so freshness does not regress.
  • Do (b) with 100 suburbs first and time the build; scale to 500 only if the build stays under the current time plus 25%.
  • Do (c) on a staging database URL first, run npm test and a preview deployment, and set the breaker to trip on crawler user agents only in its first version.
  • Watch Bing's daily 5xx count from the Webmaster API for 14 days after each step (R2). It is the only daily crawl-error signal available.
Ship when(a): second-request HIT on both routes in preview. (b): build time within budget. (c): zero 5xx in Bing's series for 14 days and no user-facing 503 in Vercel logs.
RollbackEach step is its own commit. (a) and (b) revert cleanly; (c) reverts by restoring the previous DATABASE_URL.
